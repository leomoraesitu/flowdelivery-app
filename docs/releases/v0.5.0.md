# FlowDelivery v0.5.0

Release date: 2026-07-08

## Objective

Publish the payments foundation milestone on top of the v0.4.0 checkout
release, making every confirmed order persist a payment record atomically
and rendering the payment method and status in the checkout experience.

## Included

- Supabase `payments` table with explicit grants, named constraints, and
  RLS scoped to the order owner through `auth.uid()`.
- Atomic `create_order` evolution: the SECURITY INVOKER function now
  inserts the payment row in the same transaction as `orders` and
  `order_items`.
- Pure-Dart payment domain types wired into checkout contracts:
  `PaymentMethod`, `PaymentStatus`, and `PaymentSummary`; `OrderDraft`
  carries the payment method and `PlacedOrder` exposes a payment summary
  with a pending-on-delivery default.
- Checkout data layer payment mapping: payment method forwarded to the RPC
  payload, payment summary mapped from the remote response, and invalid
  remote payment values mapped to a neutral domain failure.
- `CheckoutViewModel` now sends `PaymentMethod.cashOnDelivery` explicitly
  when placing an order.
- Checkout UI payment state: localized payment method description in the
  payment section and localized payment status in the success state.
- Localized payment copy across pt_BR, pt, and en through ARB plus
  generated `AppLocalizations`; obsolete `cartCheckoutPlaceholder` key
  removed.
- Sprint 11 documentation, memory, technical debt notes, and Trello
  reconciliation after validation.

## Architecture

Payments extend the existing atomic write path without adding a new
client-side call:

```text
CheckoutPage
  -> CheckoutViewModel (explicit PaymentMethod)
  -> OrderRepository
  -> OrderRemoteDatasource
  -> Supabase RPC create_order (order + items + payment in one transaction)
```

The payment lifecycle state lives in `public.payments`; the legacy
`orders.payment_method` column remains as accepted transitional
duplication until a future approved migration slice removes it.

## Known Limitations

- Payment remains a demo cash-on-delivery method; no payment gateway
  integration, card capture, or payment status transitions yet.
- `orders.payment_method` remains as transitional duplication while
  `payments.method` is the new source of truth (accepted Sprint 11 debt).
- Delivery address is still a localized demo placeholder, not
  profile-backed data.
- Order history, order tracking, Realtime status updates, cancellation,
  and editing are future slices.
- Coupons, discounts, dynamic delivery fee, and distance calculation
  remain out of scope.
- Cart persistence across app restarts remains planned scope.
